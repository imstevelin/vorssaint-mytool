# 系統資源檢查與改善方案

日期：2026-10-18。檢查基準：目前工作目錄（HEAD `f85fc69a` 加上既有未提交修改），以及正在執行的 `/Applications/實用小工具.app` 1.0.9（10），PID 56124。未證明已安裝執行檔與工作目錄逐位元一致；以下將執行取樣與原始碼發現分開描述。本次只新增報告，沒有修改功能、切換設定或重啟程式。

## 結論與量測限制

目前沒有看到 CPU 滿載或短時間記憶體持續失控，但常駐工具仍有可削減的背景成本。第一組 `top` 的四個有效區間為 3.6%、8.0%、4.0%、7.0%，實體記憶體約 92–93 MB。第二組約 31 秒、15 個有效區間為 3.6–8.0%，區間讀數平均約 5.2%，實體記憶體約 85–88 MB；每組初始 0% 快照不作區間判讀。這些 CPU 百分比以單核心 100% 計。`sample` 五秒取樣的 physical footprint 為 92.2 MB，程序啟動以來峰值為 164 MB。這不是所有功能全開或完全閒置的控制實驗；當時仍有 AI 狀態動畫及音訊執行緒活動。

`sample` 中反覆出現 `DisplayWindowMemoryService.scan → visibleWindows → AXUIElementCopyAttributeValue`、`NotchWindowHost.refreshMissionControlState` 及 `NotchAgentAnimationView`。其中 AX 呼叫有跨程序等待，取樣命中數不能直接當成 CPU 佔比或各模組耗能排名。原始取樣暫存於 `/tmp/vorssaint-resource-sample.txt`。

本次涵蓋功能啟停、定時器／背景工作、輸入事件、視窗／縮圖、動態島、音訊、系統監控、剪貼簿、AI 日誌，以及錄影／媒體處理的重要路徑。沒有逐一操作所有功能、長時間做洩漏測試或量測 GPU／WindowServer 的可歸因耗能，因此不能保證其餘路徑沒有問題。

## 優先改善

### 1. 視窗記憶每半秒在主執行緒做完整 AX 掃描（優先高；執行取樣已觀察到）

位置：`Sources/Vorssaint/Services/WindowLayout/DisplayWindowMemoryService.swift:72,279,312`。

每 0.5 秒重新列出螢幕視窗，再對每個應用查 AXWindows、搜尋對應視窗並讀取角色、子角色、可調整尺寸、最小化按鈕、modal、全螢幕等屬性。每次掃描的 AX 快取只活到該輪結束。視窗越多、對方 App 回應越慢，成本越高；0.1 秒 messaging timeout 也只是個別元素呼叫的限制，整輪仍可能累積多次等待。即使滑鼠正在拖曳，仍會進入 `visibleWindows()`。

方案：以 AXObserver 的視窗建立／移動／尺寸事件和工作區事件標記變動，合併 100–250 ms 的事件；快取每個 PID／視窗 ID 的 AX 對應及資格，關閉或程序退出時移除。只對變動視窗查詢；保留 5–10 秒一次的補漏掃描。拖曳期間暫停學習掃描，放開後再取穩定狀態。AX 查詢放到單一背景佇列，主執行緒保留 AppKit 讀取和最後套用動作，並設一輪總時間預算及只允許一輪在途。

先保留現有「一次還原、拖曳抑制、穩定 1.5 秒才學習、跨螢幕 transition generation」規則。事件支援不完整時走慢速補漏，避免省資源後漏掉新視窗。

驗收：10／30／60 個視窗下比較 CPU、AX 查詢次數和主執行緒停頓；測試拖曳、手動縮放、最小化、切換 Space、螢幕重接及不回應的 App。

### 2. 視窗記憶反覆整份編碼與順序造成的假變動（優先高；原始碼確認）

位置：同檔 `:199,229,268`。

每個視窗完成學習時，在迴圈中呼叫 `persist()`，將整份 memory JSON 編碼後送入 UserDefaults；同輪可能做多次。配置清單來自 WindowServer 的順序，直接以陣列相等比較；前後層級順序變動也可能觸發寫入，即使幾何沒有改變。這表示重複序列化／偏好設定更新風險，不能直接推算成相同次數的實體磁碟寫入。

方案：一輪只標記 dirty，結束後合併保存；採用穩定排序／不依賴 Z-order 的配置比較，以及與還原匹配一致的幾何容差。停止拖曳後延遲約 1 秒保存，設最長等待時間，退出或休眠前補存。需要保留疊放順序時，將它與幾何分開管理。資料量增加後，改為專用 Application Support 檔案、背景編碼及原子替換。

驗收：純切換前景 App 不應增加幾何保存次數；一次多視窗學習只保存一次；結束程序再開啟仍能還原。

### 3. 視窗標題記憶缺少容量與過期政策（優先高；長期風險）

位置：`Sources/Vorssaint/Services/WindowLayout/DisplayWindowMemorySupport.swift:14,26,81`。

`openingFrames` 與 `sizes` 以 bundle ID 加標題摘要儲存；記錄新標題時會增加項目，沒有項目數上限、最後使用時間或過期清理。只要 WindowServer 提供不同標題，文件、瀏覽器等長期使用就可能累積資料。螢幕資料也沒有總量上限。記憶體會隨記錄增長，並放大上一項整份編碼的成本。這是資料保留無上限，尚未量測到本機已經累積到異常大小。

方案：保留每 App 的通用尺寸；標題專屬配置採 LRU（例如每 App／螢幕最多 50 筆），加上全域 2,000 筆或編碼後 1–2 MB 預算、90 天過期。上限是起始設計值，應以實際使用調整；遷移舊資料時保留通用配置及最近仍在使用的視窗。

驗收：產生一萬個不同標題後資料仍受限，常用配置及現有視窗優先保留。

### 4. 動態島持續列出全系統視窗（優先中；執行取樣已觀察到）

位置：`Sources/Vorssaint/Services/Notch/NotchWindowHost.swift:519,547,799`。

動態島顯示期間，Mission Control 偵測平常每 0.25 秒呼叫 `CGWindowListCopyWindowInfo`，overview／隱藏狀態時 timer 間隔降至 0.08 秒。現有設計已把較昂貴的 frame probe 限制在必要情況，但常駐視窗清單輪詢仍存在；多螢幕鏡像的每個 host 也可能重複查詢。

方案：由共用服務取得一次 WindowServer 快照，再分發給各 host；平常降低至 0.5–1 秒，工作區／相關通知時立即查詢，確認 overview 後短時間加速。不要只靠 Space 切換事件，否則可能漏掉 Mission Control；維持慢速補漏。

驗收：以單／雙／三螢幕量測查詢次數；驗證 Mission Control、App Exposé、Show Desktop、全螢幕切換的隱藏及恢復延遲。

### 5. 錄影游標軌跡在記憶體持續累積（優先中；只影響長錄影）

位置：`Sources/Vorssaint/Services/Recorder/RecorderPointerSampler.swift:41,130`、`RecorderMotion.swift:19`。

錄影期間以 125 Hz 保存 Sample 和 identity，即使位置不變也新增，沒有持續時間或緩衝上限。按目前 64 位元結構約 40 bytes Sample 加 8 bytes identity 估算，一小時 450,000 筆約 21.6 MB 原始資料；尚未包括 Array 額外容量、游標圖、封裝及編輯時的複本。這是估算，並非實測總記憶體。只在錄影中運作，不能拿來解釋目前的背景 CPU。

方案：以固定大小區塊寫入錄影專案的暫存軌跡檔，記憶體只保留最近區塊；對靜止片段保留起止時間，匯出前再重建等距樣本。評估依錄影幀率採 60／120 Hz，並驗證高速游標與點擊精度。

驗收：連錄兩小時觀察軌跡記憶體是否趨平，驗證暫停／繼續、形狀切換、點擊對齊、取消及暫存檔回收。

### 6. 媒體編碼等待 writer 時每 2 ms 醒來（優先中低；只影響轉檔）

位置：`Sources/Vorssaint/Services/Media/MediaVideoTargetEncoder.swift:184`。

Writer 暫時無法接受資料時以 `Thread.sleep(0.002)` 輪詢，等待期間理論上可達約 500 次／秒喚醒。轉檔本來就會耗用 CPU／GPU，但這段等待可避免。

方案：改用 `requestMediaDataWhenReady` 的序列佇列驅動，保留音畫時間戳交錯、取消、錯誤和有界緩衝；可參考現有 `RecorderExporter` 的 writer readiness 實作。

驗收：大型影片與慢速目的地比較 CPU、喚醒次數和完成時間，檢查音畫同步、目標大小重試及取消。

## 次要改善與已存在的保護

- 藍牙音訊恢復每 3 秒在主執行緒查路由。可改用 CoreAudio 屬性 listener 加低頻補漏；`isConfigured` 可能同步等候 sudo 最長 3 秒，適合移到背景佇列。取樣只看到少量路由檢查，不能認定是主要 CPU 來源。改動需保留 cooldown／重連防循環。
- AI 日誌已有檔案事件、增量讀取、近期／活躍日誌才啟動的 2 秒輪詢及五分鐘保存。啟動／rescan 仍會列舉歷史目錄；資料很多時可加取消檢查、索引及掃描預算。`AgentUsageService.settleArchive` 使用主執行緒 `queue.sync` 等候完整保存，較大的歷史資料應做非同步停用，退出再設有界等待。尚未量測到此處卡頓。
- 裝飾動畫已限制最高 30 FPS，且視窗不可見／被遮蔽時停下；仍會在可見時持續合成。可提供省電模式（10–15 FPS 或靜態圖示），這屬外觀與耗能取捨，沒有證據顯示動畫失控。
- 系統監控已有按需求採樣、不同指標節奏、背景佇列、在途合併及略過無新資料的發布；不建議一律關閉必要監控。
- 縮圖快取已有 48 張／64 MiB 上限及 memory pressure 清理；有界快取仍會佔用記憶體，但沒有看到無上限快取問題。
- 剪貼簿已有 changeCount 檢查、背景讀取、單次在途防護、timer tolerance 與保存限制；Dock 滑鼠移動已有遠離區域快速略過。Focus Follows Mouse 的 0.05 秒 timer 是待評估期間才開，並非無條件常駐。
- 音量混音器只在需要音量／路由調整時建立 tap，還原後會釋放；即時頻譜有 30 Hz 更新與暫停後釋放。動態島 session teardown 也會停止音訊、AI 等來源。應保留這些生命週期保護。
- 螢幕 Watch 的 1–2 秒擷取／辨識是使用者明確啟動的工作，已有未變畫面不重做文字判讀的設計。須與常駐背景成本分開評估。

## 建議執行順序與共同驗收

先做視窗記憶的保存合併、穩定比較與容量上限，再導入事件驅動／背景 AX 查詢，接著共用動態島視窗快照。長錄影與轉檔列為第二階段。

每次以相同設定、視窗數、螢幕、音訊狀態各量測至少五分鐘，建立完全閒置、一般使用、視窗拖曳／重接、AI 活動、音訊播放、長錄影等情境。記錄程序 CPU、physical footprint、喚醒次數、主執行緒最長停頓、AX／WindowServer 查詢數、序列化次數／資料量；GPU 和 WindowServer 要另行量測，不可把整個系統變化都歸因到本 App。

建議第一階段目標是穩定視窗下完整 AX 掃描次數下降至少 80%，幾何沒有變動時不做配置寫入，歷史記憶有明確上限；節省多少 CPU／電力必須實作後量測，這次不預先宣稱百分比改善。
